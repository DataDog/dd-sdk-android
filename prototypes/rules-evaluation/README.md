# Kotlin Rules Evaluation Prototype

Benchmark-only companion to the Swift prototype and React Native mobile-flags
benchmark. Tracking: [FFL-3347](https://datadoghq.atlassian.net/browse/FFL-3347).
This standalone build is not included in the shipping Android SDK module graph.
It adds no public SDK API and does not implement a production provider.

Related work:

- [Mobile SDK building blocks and benchmarks RFC](https://docs.google.com/document/d/1BctyUHEHCAzbB2LBinYm5k5lQ9OldGEZwzdtaP62QWE/edit)
- [Swift evaluator prototype](https://github.com/DataDog/dd-sdk-ios/pull/3239)
- [React Native benchmark harness](https://github.com/DataDog/dd-sdk-reactnative/pull/1453)

## Scope

- Client UFC protobuf and ProtoJSON parsing with generated protobuf-java models.
- The same boolean workloads as the Swift prototype: static, string membership,
  compound numeric targeting, and MD5 percentage splits.
- Configuration replacement and context changes without fetching.
- Native-direct decoder/evaluator controls and warm-file-cache hydration.
- Explicit errors for unsupported conditions and malformed indexes.

This is not full UFC conformance. It does not cover regex, semantic versions,
obfuscated targeting, all variation types, or arbitrary floating-point string
coercion. A missing implementation must not be interpreted as a default result.
The RN adapter owns serialization, worker scheduling, result conversion, and
platform-specific reporting; this module owns only parsing/evaluation and the
benchmark operations. No cross-platform native library is introduced.

## Dependencies and Provenance

Kotlin 2.0.21; JDK/JVM target 17; protobuf-java, protobuf-java-util, and protoc
3.25.5; protobuf Gradle plugin 0.9.4. The full Java protobuf runtime is used for
ProtoJSON support. These choices belong to the experiment, not the production
SDK dependency policy or an APK-size recommendation.

## Unit Tests

With JDK 17 and Gradle 8.10.2 (validated locally):

```sh
gradle -p prototypes/rules-evaluation --no-daemon --max-workers=2 test
```

The RN benchmark Gradle 8.12 wrapper can also invoke this standalone project
using `-p`; the Android SDK repository's root Gradle 9 wrapper is not the build
used for this experiment. `DD_FLAGS_KOTLIN_BUILD_DIR` optionally relocates build
output to a workspace directory.

The focused tests validate both decoders against the JS results and metadata,
ignoring only the evaluation timestamp. They also cover A/B/A context changes,
replacement, failed-install preservation, unsupported/cyclic rules, missing
targeting keys, zero shards, hydration, and timing-control checksums.
Host JVM unit tests establish correctness, not Android/ART performance.

## Android Emulator Runs

Use the RN branch `sameerank/mobile-flags-benchmarks`, with
`DD_FLAGS_KOTLIN_PROTOTYPE_PATH` pointing to this directory. Its
Android extension contains build and run instructions in
`benchmarks/src/flags/README.md`. That extension was validated locally but still
needs to be pushed to the companion RN PR; the Kotlin-only unit tests above do
not depend on it.

The runner and native adapter reject physical Android devices. Compare the six
placements within one Release/Hermes emulator, retaining Android evidence
separately from iOS. Match the emulator image to the host CPU and use hardware
acceleration. Record ART/OS/ABI/compiler versions, configuration size, warmups,
and run order. Do not treat desktop JVM results or software CPU emulation as
substitutes for Android emulator measurements.

Validation on 2026-09-29: eight focused Kotlin tests pass, and the RN Release
ARM64 APK compiles this prototype and its TurboModule adapter. The real bridge
smoke test, full decode/evaluation placement benchmark, and 810-sample persisted
hydration experiment passed on a hardware-accelerated Android 15 / API 35
emulator. See `benchmarks/src/flags/ANDROID_RESULTS.md` in the RN branch for the
measurements and limitations once the Android extension is published. Raw
reports, source snapshots, and hashes are retained locally, not in this PR.
No physical Android device was used, and Android native tracking is not part of
these measurements.
